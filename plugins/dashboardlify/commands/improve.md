---
description: One command for an existing dashboard: measure it, decide what it needs (colors, layout, components), do it, and prove the change is visible
argument-hint: <url | file.html | --src dir> [--copy]
---

Use the dashboardlify skill (Skill tool, skill `dashboardlify`). This is the single front door for an existing dashboard; the user should not have to pick a mode. Target: $ARGUMENTS (if empty, ask for a URL, an html file or a source dir, once).

0. Survey. Run `scan.mjs --src <dir>` for roles and routes, or ask the user when the target is a URL or file or the ROLES block says none found. Build the pages x roles x states matrix per [survey.md](../skills/dashboardlify/references/survey.md) (ask for test accounts or a `--storage-state` file kept outside the repo; never print or commit credentials). Measure each reachable cell with `--inventory --status`; mark the rest source-checked or not covered with the reason.
1. Measure. Run `node <skill dir>/scripts/scan.mjs <target> --status --design --shot before.png --json before.json`. `--status` implies `--inventory`. Print the value verdict, the PALETTE verdict, the LAYOUT verdict, the STATUS verdict and the DESIGN verdict in short lines.
2. Decide from the verdicts and print the plan in one line each. Run the needed passes in this order and skip the ones not needed:
   - PALETTE ADJUST or REPLACE, or value verdict TIGHTEN: Mode B (tokens, spacing, type, color, radius, icons, motion). PALETTE REPLACE changes a brand hue: ask first.
   - LAYOUT ARRANGE: Mode D (CSS-only layout).
   - STATUS FIX with css issues (status-mixed-style, status-word-colors, status-too-many-colors, status-low-contrast): Mode B may apply the status colour mapping from [status.md](../skills/dashboardlify/references/status.md) as VALUES ONLY; it never changes font family, sidebar colour or accent hue.
   - Any INVENTORY SWAP, or STATUS jsx issues (status-plain, status-color-only): Mode C. (STATUS covers any repeated short label or badge in any words; status-plain fires only on a plain column that looks like a state.) The brief lists the component swaps per rule (rule id, component, suggested visual) and three change groups: status ([status.md](../skills/dashboardlify/references/status.md)), content ([content.md](../skills/dashboardlify/references/content.md)) and identity.
   - IDENTITY ([identity.md](../skills/dashboardlify/references/identity.md)): offer it when the screen has no strong identity or the user asks for a bigger visible change. Show the 2-3 preset choices with a one-line rationale each and WAIT for the user. Never apply one silently; if declined, keep the existing identity.
   - LAYOUT REWORK, value verdict REWORK, or JSX-only issues left (placeholder widgets, wrapper markup, component structure): Mode C. It needs an approved brief, so write the brief and stop for approval before editing anything for this part. Apply the B and D parts first.
   - DESIGN FIX: decide every finding with [design-checks.md](../skills/dashboardlify/references/design-checks.md), section "How the AI decides": CHANGE (evidence is real, the fix fits the current mode: apply the smallest one), KEEP (state the reason, such as a deliberate brand accent or a desktop-only product) or ASK (needs a brand or intent decision; never change identity in Mode B). Never change anything on scan output alone when a screenshot or the context contradicts it. Print a decisions table (rule, evidence, CHANGE / KEEP / ASK, action or reason); the separate `PHONE` line gets a row only when it is FIX (SKIP and OK get none) and carry the ASK items into the question or the brief.
   - All four OK/KEEP/LEAVE (DESIGN OK or all KEEP): say the screen is already tight, give at most 3 refinements, stop.
3. Follow the steps of each chosen mode in SKILL.md exactly (scope, pass order, JSX rules, no commit or stage).
4. Verify with `scan.mjs <target> --status --design --compare before.json --visible-change before.png --shot after.png`; it prints `Design: X -> Y`. NOT VISIBLE (<3%) or SUBTLE is never reported as done: diagnose and say why. With `--src` the gate cannot run: say so.
5. Report: every survey cell as covered (rendered or source-checked) or not covered with the reason, the INVENTORY verdict per cell, the verdicts before and after (value, PALETTE, LAYOUT, STATUS, DESIGN), the design decisions table (CHANGE / KEEP / ASK per finding), which status and fit rules fired and which were fixed, the visible-change percent, files changed, and anything left with the one command or mode that handles it.

`--copy` also rewrites copy in Mode B. The narrower commands (`scan`, `tighten`, `arrange`, `rework`) still exist for running one step alone.
