Use the dashboardlify skill (Skill tool, skill `dashboardlify`), "Triage first" section. Target: $ARGUMENTS (if empty, ask for a URL, an html file or a source dir, once).

Run `node <skill dir>/scripts/scan.mjs $ARGUMENTS` (a URL or html file renders in Chrome; `--src <dir>` gives a source-only estimate). Print the table and the verdict exactly as the script reports them, including the PALETTE block (domain, primary, issues, KEEP/ADJUST/REPLACE verdict). Pass `--no-palette` to skip it. If the verdict surprises you, say so and why.

Flags: `--inventory` adds the INVENTORY block: `INVENTORY FIT|SWAP`, a counts line (table, chart, kpi, list, form, empty, placeholder, map, calendar, loading, error) and one line per fired fit rule `- <rule>: <type> "<label>" <detail> -> <suggest>` (rules: [metric-to-visual.md](../skills/dashboardlify/references/metric-to-visual.md) "Component fit"); SWAP means a component should change, route to Mode C. `--status` (implies `--inventory`) adds the new fit rules `table-status-to-rows`, `long-list-no-filter`, `flat-dates-to-groups`, `people-list-to-capacity`, `kpi-no-context`, the advisory rules `search-no-shortcut` and `no-page-summary` (never change the verdict), and a STATUS block over categorical labels (any repeated short label or badge, any words; found structurally, not from a word list): `STATUS OK|FIX|NONE  (n labels, n words, n styles, n colours)` plus one line per issue `- status-<rule>: <detail> -> CSS fix (Mode B) | markup fix (Mode C brief) (status.md)` (ids: `status-plain`, `status-mixed-style`, `status-word-colors`, `status-too-many-colors`, `status-low-contrast`, `status-color-only`; rules in [status.md](../skills/dashboardlify/references/status.md), content rules in [content.md](../skills/dashboardlify/references/content.md)). STATUS FIX does not turn INVENTORY into SWAP. Word lists are English-only and detection is heuristic: confirm each hit by hand. `--no-palette` combines with it; JSON gains `inventory.status` per target and `aggregate.inventory.status`; `--compare` prints `Status: X -> Y`. `--design` (opt-in, independent of `--status`, works alone or together) adds a DESIGN block: `DESIGN OK|FIX|NONE  (accent <hue> in N roles, N button fills, N hues, type Nx (N styles near largest), neutral ~N%, grouping Nx, loud N)` plus one line per finding `- <rule>: <numbers> -> CSS fix (Mode B) | markup fix (Mode C brief) (design-checks.md)` (ids: `accent-no-job`, `primary-button-styles`, `no-focal-point`, `too-many-hues`, `weak-grouping`, `contrast-overspent`), an `advisory: squint: ...` line that never changes the verdict (names what the heaviest region holds and whether it covers a largest-size text), and a separate `PHONE OK|FIX|SKIP` line (rule `phone-size`): `PHONE SKIP (page declares a desktop viewport or none)` when the viewport meta lacks width=device-width, otherwise the page is re-measured at 390px wide after everything else and the line gives counts plus a `- phone-size:` finding. PHONE never changes the DESIGN verdict. Rules, thresholds and the CHANGE / KEEP / ASK decision per finding: [design-checks.md](../skills/dashboardlify/references/design-checks.md). All of it is heuristic, so confirm each hit by hand. JSON gains `design` and `phone` per target and `aggregate.design`, `aggregate.phone`; `--compare` prints `Design: X -> Y` and `Phone: X -> Y`. Without `--design` the output is unchanged. `--storage-state <file>` loads a Playwright-style storage state (cookies and localStorage, or a bare cookie array) before navigating; keep the file outside the repo; the scan prints only `auth: N cookies, M storage keys`, never values; a missing file exits 2. `--block <pattern>` (repeatable) blocks matching requests so the page shows its error or empty state. `--src` also prints a ROLES block (`ROLES a, b | guards n | routes n (k guarded)` and a route table, or `ROLES none found in source: ask the user`). The survey procedure is in [survey.md](../skills/dashboardlify/references/survey.md). `--json <f>`, `--compare <before.json>`, `--dark`, `--width <n>`, `--no-palette`, `--combo calm|paper|brand` (colour combo reported in the PALETTE block: calm for dense data, paper for warm or consumer products, brand for brand-heavy ones), plus the layout flags: `--shot <file.png>` saves the first-screen PNG, `--visible-change <before.png>` compares against an earlier shot and prints `VISIBLE CHANGE n% of the first screen changed: VISIBLE (>=8%) | SUBTLE (3-8%) | NOT VISIBLE (<3%) | INCOMPARABLE` (different width: exit 1; same width with a different height is cropped; `--shot` and `--visible-change` must be different paths, exit 2 if equal), `--height <px>` sets the first-screen height (default 900), `--no-layout` skips the layout checks. Print the LAYOUT block (`LAYOUT OK|ARRANGE|REWORK`: OK = score under 3 or only low-weight JSX notes, ARRANGE = score 3+ fixable by CSS even with JSX-only notes left, REWORK = JSX-only high-weight issues dominate (score 14+ with 2+ JSX issues, or 5+ with a weight 2+ JSX-only issue); and the issue lines `- id: detail -> fix class (css|jsx) -> recipe: <id>`) and the `NEXT:` line as reported. The JSON holds `layout:{verdict,score,issues,metrics}` and `visibleChange:{percent,verdict}`.

Make NO edits. Do not commit or stage. Finish by recommending the next command: LEAVE -> nothing (or up to 3 refinements), TIGHTEN -> /dashboardlify:tighten, REWORK -> /dashboardlify:rework. When the LAYOUT verdict is worse than the value verdict, follow the NEXT line: /dashboardlify:arrange (CSS-only layout) or /dashboardlify:rework.
